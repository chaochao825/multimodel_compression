# EXP-053: Exact Wan VAE temporal-scheduling Gate

- Claim: C-031
- Candidate: L-031
- Gate: G-032
- Lane: integrate
- Status: frozen
- Date: 2026-09-01

## Decision question

Can the unchanged BF16 Wan VAE preserve bitwise decoded tensors while grouping
causal latent frames, and does that exact scheduling change improve the
`9.637995s` resident rCM4 endpoint by at least `1.10x` on one H200?

## Frozen baseline and workload

- Incumbent: EXP-052 resident rCM4, F81 median request `9.637995s`, VAE
  `4.308300s`, denoiser `3.205365s`.
- Source, checkpoint, prompt, seed, scheduler, rCM weights, BF16 dtype,
  attention backend, VAE weights, output transfer, and MP4 serialization remain
  inherited from EXP-047/052.
- F17 uses the existing smoke prompt and seed. F81 uses prompt indices
  `0/1/2/3` and seed `2026082701`.
- Exactly one isolated H200 NVL must be visible. No foreign process may share
  the selected GPU during a measured stage.

## Candidate and mutable surface

The official VAE source is immutable. A separate harness may only replace the
outer decode schedule:

1. clear the official feature cache;
2. apply the unchanged scale transform and `conv2`;
3. decode latent frame 0 alone;
4. decode later frames in regular chunks from the frozen grid `1/2/4/8`, using
   the same feature-cache objects and resetting only the official conv index;
5. concatenate outputs once and clear the cache.

All Conv3d, RMSNorm, attention, upsample, weights, dtypes, and cache values are
unchanged. `chunk=1` isolates one-shot concatenation from larger dispatch groups.

## Stages

### S0: local schedule validation

Run deterministic unit tests for first-frame separation, complete/nonoverlapping
temporal ranges, output ordering, and cache-object forwarding. Run syntax,
lint, and diff checks. This stage does not establish CUDA equality.

### S1: F17 exact screen

Generate one frozen rCM4 F17 latent. On that same tensor, run official decode
and each chunk candidate. Require identical shape/dtype and `torch.equal`.
Record maximum absolute and relative-L2 diagnostics without using them to relax
the exact guard. After one warmup, collect three CUDA-event complete-decode
samples and peak reserved memory per path.

Select the lowest-median bitwise-exact chunk. If none exists, stop. A candidate
that is numerically close but not bitwise equal is ineligible.

### S2: four-prompt F81 component confirmation

Use only the S1-selected chunk. For each frozen prompt, produce the rCM4 latent
once and interleave official/candidate complete VAE measurements on that tensor.
Collect three CUDA-event samples per path, exactness, and peak memory.

Advance only if all four prompts are bitwise equal, aggregate complete-VAE
speedup is at least `1.26x`, projected resident request speedup is at least
`1.10x`, and no OOM/fallback/foreign process occurs.

### S3: complete resident endpoint

Run the four frozen prompts through the unchanged EXP-052 resident rCM4 service
with only the selected exact decode schedule. Include text, denoising, VAE, CPU
transfer, and MP4 serialization. Report raw rows and median component/request
times against the immutable `9.637995s` incumbent.

## Primary endpoint and guards

Pass requires all of:

- bitwise equality for every F17 and F81 decoded tensor;
- complete VAE median speedup `>=1.26x` in S2;
- complete resident request median `<=8.761814s`, equivalent to `>=1.10x`
  incremental speedup over EXP-052;
- four rCM network calls, no output truncation, OOM, fallback, foreign process,
  or peak reserved memory beyond physical H200 capacity.

## Outcome mapping

- `pass`: every exactness guard passes and S3 reaches `>=1.10x` incremental
  resident speedup.
- `speed-boundary`: exact and faster, but S2 or S3 misses the materiality guard.
- `null`: exact candidates provide no repeatable complete-VAE improvement.
- `adverse`: exact scheduling is slower or causes prohibitive memory growth.
- `exactness-null`: no chunk candidate remains bitwise equal; stop before S2.
- `invalid`: identity, selection, isolation, workload, or timing boundary is
  violated.
- `engineering-failure`: S0/S1 cannot run after at most two bounded repairs
  without changing the candidate contract.

## Resource cap and stop rule

- One isolated H200 NVL, at most two GPU-hours and 5 GiB new artifacts.
- At most two bounded engineering repairs.
- Stop on one valid G-032 outcome, any isolation/identity violation, no exact S1
  candidate, failed S2 advance guard, resource exhaustion, or user interruption.
- Do not add compile, CUDA Graph, FP8, attention kernels, codec overlap, new
  prompts/seeds, or approximate quality evaluation inside EXP-053.

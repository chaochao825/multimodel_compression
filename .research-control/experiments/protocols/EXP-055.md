# EXP-055: Exact full-F81 Wan VAE CUDA Graph replay

- Claim: C-033
- Candidate: L-033
- Gate: G-034
- Lane: integrate
- Status: frozen
- Date: 2026-09-02

## Decision question

Can one CUDA Graph capture/replay of the unchanged complete official BF16 Wan
VAE decode remove enough launch overhead to improve the exact resident rCM4
request by at least `1.05x` without changing a decoded bit?

## Theoretical boundary

The accepted conditional-redundancy and dual-time analyses explain why fixed
BCM, low-rank residual, and post-hoc state closure fail when their coordinates
are not cheaply observable. EXP-055 does not approximate a state, transport a
feature, or change the denoising trajectory. It tests only exact execution
redundancy in a fixed operator graph. A pass or null therefore updates the
launch-bound VAE systems claim only; it cannot support or refute conditional
state, thermodynamic, support-state, or physical-time transport claims.

## Frozen baseline and implementation

- Baseline: L-030 / EXP-052 resident rCM4 at `9.637995031895116s` median F81
  request and `4.308299851138145s` median VAE.
- Source, checkpoint, rCM steps, noise, prompts, text policy, official
  `tokenizer.decode`, frame order, causal-convolution caches, BF16 kernels,
  transfer, serialization, and output geometry remain unchanged.
- Candidate: exactly one `torch.cuda.CUDAGraph` containing the complete official
  VAE decode for a fixed shape. Capture uses a side-stream warmup, one
  long-lived static input, one long-lived static output, and graph-owned memory
  retained through final replay.
- Every measured replay includes the new-latent `copy_`, graph replay, required
  synchronization, and an output handoff with independent ownership. Bare
  replay time is diagnostic only.
- Eager references use fresh official decoder cache state. Distinct inputs are
  replayed in alternating order to expose stale state.

## Identities

- S0 uses the registered EXP-047 smoke prompt at F17 with seeds
  `2026082700`, `2026082703`, and `2026082704`.
- S1/S2 use EXP-052 prompt indices `0,1,2,3` at seed `2026082701` and the same
  on-policy rCM4 latents.
- No input, timing, or output may select a graph variant. There is only one
  registered graph action.

## S0: F17 engineering and stale-state screen

1. Verify exactly one visible isolated H200 and the frozen source/checkpoint.
2. Produce the three deterministic on-policy F17 latents without decoding.
3. Decode each input eagerly with fresh official cache state.
4. Warm on a side stream, capture the complete decode once, and replay the
   sequence `0,1,2,1,0` with input copy and owned-output handoff.
5. Require `torch.equal` for every graph/eager GPU tensor, finite outputs,
   correct shape/dtype/device, and equality between repeated occurrences of the
   same input.

Stop as `engineering-null` if capture cannot run after at most two bounded
repairs. Stop as `exactness-null` on any mismatch or stale-state result.

## S1: F81 exactness and component materiality

1. Use the four registered F81 on-policy rCM4 latents and independent eager
   references.
2. Replay all four inputs for at least two rounds after warmup, alternating
   order, with identical synchronization and ownership.
3. Require bitwise-equal GPU and decoded CPU tensors, unchanged network-call
   count, finite timings, and peak reserved memory at most `59948 MiB`.
4. Interleave eager and graph complete-decode samples. Require median
   complete-VAE speedup at least `1.12x`.
5. Project against the full EXP-052 component row and require resident request
   speedup at least `1.05x` before S2.

## S2: complete resident request

Run the exact EXP-052 resident rCM4 endpoint with graph VAE for the same four
prompts and seed. Include positive text encoding, denoising, graph input copy,
VAE replay, output handoff, GPU-to-CPU transfer, and MP4 serialization.

Promotion requires:

- decoded CPU tensors bitwise equal to eager;
- four network calls and every request/output guard valid;
- median request at most `9.1790428875s`, equivalent to `>=1.05x`;
- peak reserved memory at most `59948 MiB`.

Record `1.25x` VAE and `1.10x` request as stretch diagnostics only.

## Prohibited changes

No temporal regrouping, `torch.compile`, custom convolution, kernel fusion,
FP8/quantization, cache approximation, model/scheduler change, codec/preset
change, asynchronous response contract, threshold relaxation, or second graph
variant is allowed.

## Outcome mapping

- `pass`: S0, S1, and S2 exactness, memory, and speed guards pass;
- `speed-boundary`: S1 is exact and material but S2 misses `1.05x`;
- `performance-null`: exact S1 remains below `1.12x` VAE or `1.05x` projected
  request speed;
- `exactness-null`: any runnable graph output differs bitwise or is stale;
- `engineering-null`: capture cannot run within two bounded repairs;
- `invalid`: source, identity, isolation, timing, output, or resource guards
  are violated.

## Resource cap and stop rule

- One isolated H200 NVL, at most two GPU-hours, 5 GiB new artifacts, and two
  bounded engineering repairs.
- Stop at the first valid terminal outcome, isolation loss, resource cap, or
  user interruption.
- The second idle H200 is not part of EXP-055 and must not be used to overlap a
  second scientific candidate.

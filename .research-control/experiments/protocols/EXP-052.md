# EXP-052: Exact resident-text rCM warm-runtime Gate

- Claim: C-030
- Candidate: L-030
- Gate: G-031
- Lane: integrate
- Status: frozen
- Date: 2026-09-01

## Decision question

Does removing per-request UMT5 reconstruction, while still encoding every new
positive prompt and changing no numerical operation, close the released rCM
warm-service end-to-end gap on one H200?

## Frozen baseline and workload

- Baseline identities, code source, checkpoints, scheduler, dtypes, attention
  backend, resolution, frame count, and serialization are inherited unchanged
  from EXP-047.
- Methods remain ordered as `teacher20`, `native4`, and `rcm4`.
- F81 timing uses the four frozen EXP-047 prompts, each exactly once per method,
  with seed `2026082701`.
- The primary workload is a persistent warm service. Pipeline and UMT5 model
  initialization are measured separately; each timed request includes positive
  tokenization/UMT5 forward, denoising, VAE decode, CPU transfer, and MP4
  serialization.
- No positive-prompt embedding may be reused. The globally fixed negative
  prompt may be cached after one exact encoding.

## Candidate and mutable surface

Only the lifetime policy in a new EXP-052 harness may change:

1. keep the official global UMT5 encoder resident across distinct requests;
2. retain one exact embedding for the frozen negative prompt;
3. clear both at process shutdown.

The official rCM repository, model modules, checkpoints, Wan arithmetic,
samplers, VAE, attention implementation, prompts, seeds, and output codec are
immutable. EXP-047 files are not edited or overwritten.

## Stages

### S0: text-only screen

On one isolated H200, compare clear-after-request and resident policies over
the same four distinct positive prompts. For native policy, include the same
fixed negative prompt. Record first-request initialization, subsequent text
latency, peak allocated/reserved memory, and `torch.equal` for every embedding.

Advance only if:

- every positive and negative embedding is bitwise equal;
- resident median request text latency saves at least `5.5s` against the
  matched clear-after-request policy;
- no OOM, fallback, NaN, or foreign GPU process occurs.

### S1: exact F17 generation smoke

Run each method once under clear and resident policies on the frozen EXP-047
smoke identity. Compare the decoded CPU video tensor with `torch.equal` before
serialization and require identical network call counts. Resident UMT5 and the
full Wan/VAE pipeline must coexist on the same H200.

Advance only on exact equality for all three methods and no OOM/fallback.

### S2: four-prompt F81 warm-service Pareto

For each method, load one process, warm UMT5 outside timed requests, then run
the four distinct prompts sequentially. Positive embeddings are recomputed.
Report raw per-prompt and median text, denoiser, VAE, CPU transfer,
serialization, complete request latency, VRAM, and network calls.

## Primary endpoint and guards

Primary endpoint:

\[
S_{\mathrm{warm}}=
\frac{\operatorname{median}_p T_{\mathrm{teacher20,resident}}(p)}
     {\operatorname{median}_p T_{\mathrm{rcm4,resident}}(p)}.
\]

Pass requires all of:

- `S_warm >= 2.5x`;
- exact S0 embeddings and exact S1 decoded videos;
- rcm4 network calls remain four and teacher20 calls remain forty;
- no positive embedding cache, OOM, fallback, incomplete output, or foreign
  H200 process;
- peak reserved memory remains below physical H200 memory.

The native4 row is a matched NFE control and must be reported but does not
decide the primary pass.

## Outcome mapping

- `pass`: every exactness guard passes and resident rCM reaches `>=2.5x` versus
  the identically optimized resident teacher.
- `speed-boundary`: exactness passes and runtime improves, but the primary
  speed ratio remains below `2.5x`.
- `null`: S0 exactness passes but saves less than `5.5s/request`; stop before
  F81 and move the bottleneck to measured VAE/serialization work.
- `adverse`: resident lifetime is slower, causes OOM, or materially increases
  memory without compensating latency.
- `invalid`: identity, policy, GPU isolation, or timing-boundary violation.
- `engineering-failure`: implementation cannot reach S0/S1 after at most two
  bounded repairs without changing the frozen computation.

## Resource cap and stop rule

- One isolated H200 NVL, at most four GPU-hours and 10 GiB new artifacts.
- At most two bounded engineering repairs.
- Stop immediately on a valid S0 null/adverse result, exactness failure,
  resource exhaustion, invalid isolation, or one valid G-031 outcome.
- No FP8, sparse attention, compile, CUDA Graph, cache approximation, new
  prompt, new seed, or quality metric may be added inside EXP-052.
